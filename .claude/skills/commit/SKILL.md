# Commit

변경사항을 읽고, 한 커밋이 한 가지 의도만 담도록 나눈 다음, 사용자에게 묻지 않고 바로 커밋한다. 사용자가 이 스킬을 부른 것 자체를 커밋 승인으로 본다.

## 1. 변경사항 분석

다음을 병렬로 실행해 현재 상태를 파악한다.

```bash
git status --short
git diff              # 스테이징 안 된 변경
git diff --staged     # 이미 스테이징된 변경
git log --oneline -10 # 기존 메시지 스타일 참고
```

- 저장소가 아니면(`not a git repository`) 멈추고 사용자에게 `git init` 여부를 묻는다.
- 변경사항이 없으면 "커밋할 변경사항이 없습니다"라고 알리고 끝낸다.
- 추적되지 않은 새 파일은 `git diff`에 나오지 않으므로 `git status`에서 확인하고 필요하면 내용을 읽는다.
- 사용자가 이미 일부를 스테이징해 두었다면, 그 범위를 의도된 단위로 존중한다.

## 2. 논리적 단위로 분류

파일 목록이 아니라 **변경 의도**로 묶는다. 한 커밋은 한 문장으로 설명할 수 있어야 한다.

- 기능 추가와 그 기능의 테스트는 같은 커밋에 둔다.
- 기능 변경과 무관한 리팩터링, 포맷팅, 의존성 변경은 분리한다.
- `package.json`과 lock 파일처럼 함께 바뀌어야 하는 파일은 쪼개지 않는다.
- 한 파일 안에 서로 다른 의도가 섞여 있으면 그 파일의 주된 의도에 해당하는 커밋에 넣고, 완료 보고에서 언급한다. `git add -p` 같은 대화형 명령은 쓸 수 없다.

커밋하면 안 되는 파일은 묻지 않고 제외하고, 완료 보고에서 알린다.

- 비밀값: `.env`, `*.pem`, 자격 증명, API 키가 들어간 파일
- 산출물·임시 파일: `node_modules/`, `dist/`, 로그, 디버그용 스크립트
- 크기가 큰 바이너리

## 3. 커밋 메시지 작성

형식:

```
<type>: <요약>

<본문 (선택)>
```

| type | 쓰는 경우 |
|---|---|
| `feat` | 사용자가 체감하는 기능 추가·변경 (UI 개편 포함) |
| `fix` | 버그 수정 |
| `refactor` | 동작 변화 없는 코드 구조 개선 |
| `chore` | 빌드, 의존성, 설정, 문서, 테스트 등 그 외 |

작성 규칙:

- 요약은 한국어로, 50자 안팎, 마침표 없이 쓴다. 명사형 또는 "~한다"가 아닌 간결한 서술로 끝낸다. 예: `feat: 레트로 테마로 페이지 레이아웃 개편`
- 무엇을 바꿨는지보다 **왜/무엇을 위해**가 드러나게 쓴다. 파일 이름 나열은 피한다.
- 요약만으로 충분하지 않을 때만 본문을 쓴다. 본문은 빈 줄 다음에, 이유와 주의할 점을 짧은 목록으로 적는다.
- `git log`에 기존 스타일이 있으면 그것을 따른다.
- 세션에 커밋 attribution 지침(예: `Co-Authored-By` 줄)이 있으면 메시지 끝에 붙인다.

## 4. 커밋 실행

계획을 확인받지 않고 바로 실행한다. 커밋마다 해당 파일만 스테이징하고 커밋한다. 여러 줄 메시지는 heredoc으로 넘긴다.

```bash
git add src/App.tsx src/App.css
git commit -F - <<'EOF'
feat: 레트로 테마로 페이지 레이아웃 개편

- 흑백 크롬으로 생성된 컴포넌트만 색을 갖도록 함
EOF
```

- `git add -A`, `git add .`는 쓰지 않는다. 제외한 파일이 섞여 들어간다.
- `--no-verify`로 훅을 건너뛰지 않는다. pre-commit 훅이 실패하면 원인을 고치고 **새 커밋을 다시 만든다**. `--amend`로 이전 커밋을 덮어쓰지 않는다.
- push는 사용자가 따로 요청할 때만 한다.

## 5. 완료 보고

끝나면 `git log --oneline -<커밋 수>`로 만든 커밋을 보여준다. 아래 항목이 있으면 함께 알린다.

- 제외한 파일과 이유 (예: `.env` — 비밀값 포함)
- 여러 의도가 섞여 한 커밋에 넣은 파일
- 남은 미커밋 변경

사용자가 결과를 바꾸고 싶어 하면 그때 새 커밋으로 고친다. push된 적 없는 직전 커밋의 메시지만 고치는 경우에 한해, 사용자가 요청하면 `--amend`를 쓸 수 있다.
