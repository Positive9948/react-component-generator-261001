# TDD Rule

> **경고: 이 규칙은 Rigid다 — 상황에 맞게 변형하지 마라.**
> 예외는 아래 "적용 기준"에 명시된 대상뿐이다. 그 외의 판단으로 단계를 생략하거나 순서를 바꾸지 않는다.

## 우선순위

- 프로젝트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙을 우선한다.**
- 이 파일은 **기본값(fallback)** 이다. 프로젝트 규칙이 다루지 않는 부분에만 적용한다.

## 적용 기준

### TDD 필수

- **비즈니스 로직** (도메인 규칙, 계산, 상태 전이)
- **API** (라우트 핸들러, 요청 검증, 응답 형태, 에러 매핑)
- **유틸리티 함수** (파서, 변환기, 정규화, 포매터)
- **버그 수정** (버그를 재현하는 실패 테스트를 먼저 작성)
- 동작이 있는 훅/상태 관리 로직

### TDD 불필요

- **타입 정의** (`type`, `interface`만 있는 파일)
- **설정 파일** (빌드, 린트, tsconfig, 환경 설정)
- **순수 UI** (동작 없이 마크업과 스타일만 바꾸는 변경)
- **SQL** (스키마, 마이그레이션, 쿼리 문자열 자체)
- 문서, 주석, 정적 에셋

판단이 애매하면 **필수로 간주한다.**

## RED-GREEN-REFACTOR 사이클

### 1. RED — 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 묶지 않는다.
- 테스트 이름은 검증하는 동작을 서술한다.
- **반드시 실행해서 실패를 확인한다.** 실행하지 않은 테스트는 RED가 아니다.
- **실패 이유가 "기능 미구현"이어야 한다.** 오타, import 오류, 문법 오류, 잘못된 셋업으로 실패했다면 테스트를 고치고 다시 실행한다.
- 처음부터 통과한다면 이미 구현된 동작이거나 테스트가 잘못된 것이다. 원인을 확인하기 전에 다음 단계로 가지 않는다.

### 2. GREEN — 통과시키는 최소 코드

- **방금 실패한 테스트를 통과시키는 최소한의 코드만 작성한다.**
- **YAGNI:** 테스트가 요구하지 않는 분기, 옵션, 일반화, 예외 처리를 추가하지 않는다.
- **신규 테스트와 기존 테스트가 모두 통과**하는 것을 실행으로 확인한다.
- 기존 테스트가 깨지면 GREEN이 아니다. 테스트를 수정해 통과시키지 말고 코드를 고친다.

### 3. REFACTOR — 구조 개선

- 대상: **중복 제거, 이름 개선, 헬퍼 추출**, 불필요한 코드 정리.
- 테스트 코드도 리팩터링 대상이다.
- **매 변경 후 테스트를 실행해 green을 유지한다.**
- **새 동작을 추가하지 않는다.** 새 동작이 필요하면 RED로 돌아간다.

### 4. 반복

- 다음 동작을 하나 골라 **RED로 돌아간다.**
- 모든 요구 동작이 테스트로 덮일 때까지 반복한다.

## 삭제 강제 규칙

- 테스트보다 프로덕션 코드를 먼저 작성했다면 **그 코드를 삭제하고 RED부터 다시 시작한다.**
- **"참고용"으로 남기는 것도 금지한다.** 주석 처리, 별도 파일 보관, 다른 브랜치 보관 모두 포함한다.
- 삭제 후 다시 작성하는 코드는 이전 코드를 보지 않고 테스트에서 출발한다.

## 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트 불필요" | 단순하면 테스트도 1분이면 끝난다. 단순한 코드도 나중에 수정되며, 그때 테스트가 회귀를 막는다. |
| "나중에 추가하겠다" | 나중에 쓰는 테스트는 구현을 따라 쓰게 되어 아무것도 검증하지 못한다. 그리고 대부분 쓰지 않는다. |
| "시간이 없다" | 디버깅과 회귀 수정이 테스트 작성보다 더 오래 걸린다. 시간이 없을수록 TDD가 빠르다. |
| "삭제하면 낭비" | 매몰 비용이다. 테스트 없이 쓴 코드는 검증되지 않은 부채이며, 다시 쓰는 비용이 유지 비용보다 작다. |
| "프로토타입이다" | 프로토타입은 대부분 그대로 프로덕션이 된다. 진짜 버릴 코드라면 버려지는 시점까지 커밋하지 않는다. |
